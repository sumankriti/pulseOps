01 · What have we actually built?

PulseOps has a shell host and two runtime-federated Angular remotes. Orders and inventory are built separately, expose route arrays, and are downloaded by the shell from their own origins. Domain data is still simulated locally. The host now coordinates a demo sign-in session; this is not backend authentication.

The boundary has changedThe shell no longer compiles domain routes through TypeScript aliases. A separate shared auth-contract alias supplies a singleton token, without importing another application's source. It reads remote locations from a manifest and invokes loadRemoteModule(). Both remotes generate remoteEntry.json; the browser checks verify requests to those entries and their exposed route bundles.
RoleProjectComposition surface

Orders remotemfe-orders · 4201./Routes exports ORDERS_ROUTES
Inventory remotemfe-inventory · 4202./Routes exports INVENTORY_ROUTES

Each project also has a standalone bootstrap. The shell does not execute a remote's standalone bootstrap; it composes the exposed feature routes inside the host application.

02 · Where does execution start?

  1. Start the complete workspace.Use npm run start:all to check ports 4200/4201/4202 and start all three apps, or run the individual start commands in separate terminals. Stop old servers before startup.
  2. The CLI reads angular.json.The federation serve wrapper builds shared assets, exposed modules, and metadata, then runs Angular's underlying server. The browser entry is still the project's src/main.ts.
  3. The browser requests the host document.The root is <app-root>. The generated document loads the import-map shim and entry code.
  4. main.ts initializes federation.The shell reads federation.manifest.json, fetches remote entry metadata, and prepares shared dependency import maps.
  5. Only then is Angular bootstrapped.A dynamic import loads bootstrap.ts, whose exported function receives the runtime and calls bootstrapApplication.
  6. The router checks the demo session.An anonymous protected URL redirects to the public login page. After valid sample credentials, WorkspaceLayout mounts and loadRemoteModule('mfe-orders', './Routes') returns the remote routes. A child route loads its component into the workspace outlet.
index.html → shim + main.ts
  → initFederation(manifest) → remote metadata + import map
  → import('./bootstrap') → bootstrap(runtime)
  → App + RouterOutlet
  → loadRemoteModule('mfe-orders', './Routes')
  → remote route array → remote page

Why split startup? Angular and its shared dependencies must be resolved through the prepared import map. Importing feature components before initialization would defeat that sequence.

The document displays startup progress before Angular mounts. Fatal initialization failures display a recovery message; that is separate from a remote-route fallback.

Deep link rule: Production hosting must serve the app document for client-side routes while still serving missing JavaScript or JSON files as errors, not silently returning HTML.

03 · Bootstrap: federation first, Angular second

These are shortened excerpts from the current implementation.

// mfe-shell/src/main.ts
initFederation('federation.manifest.json', {
  hostRemoteEntry: { url: './remoteEntry.json' },
  strict: { strictRemoteEntry: false, strictExternalCompatibility: true }
}).then(runtime =>
  import('./bootstrap').then(m => m.bootstrap(runtime))
).catch(/* display fatal startup error */);

// mfe-shell/src/bootstrap.ts
export const bootstrap = (runtime: NativeFederationResult) =>
  bootstrapApplication(App, {
    providers: [provideRouter(
      createRoutes(runtime), withComponentInputBinding()
    )]
  });
  • initFederation prepares shared dependency resolution and returns a runtime with loadRemoteModule.
  • hostRemoteEntry describes the host's own shared dependency requirements. A host can generate metadata without exposing a business feature.
  • strictRemoteEntry: false allows unavailable remote entries to be skipped so the shell can still start. A route-level fallback explains the unavailable feature.
  • bootstrapApplication creates the Angular application with the standalone root App.
  • providers supplies routing services; createRoutes(runtime) gives route loaders access to the initialized runtime.
  • withComponentInputBinding() remains the router feature connecting route values to routed component inputs.

Standalone Angular components list template dependencies in imports. Those imports are distinct from dependency injection providers. There is no AppModule in this application.

05 · How does a route become a page?

The shell mounts the orders domain at orders using loadChildren with loadRemoteModule(). Its public ORDERS_ROUTES array contains relative routes: an empty path for the list and :id for details. Here is the list child route:

{
  path: '',
  pathMatch: 'full',
  loadComponent: () => import('./orders-page')
    .then(m => m.OrdersPage)
}
  • path is the URL pattern, written without a leading slash in this configuration.
  • loadComponent supplies the standalone component asynchronously when needed.
  • import(...) is JavaScript dynamic import. The build can place this code in a separate chunk.
  • .then(m => m.OrdersPage) selects the named class from the imported module.

Why? Loading a feature only when its route is needed reduces the initial code the user must download. Already loaded modules may be reused; lazy loading does not guarantee a fresh network request every visit.

The empty path uses pathMatch: 'full' so only the empty URL redirects to orders. The ** wildcard comes last so unmatched URLs reach the missing-page component.

Loading boundary versus release boundaryA component can be lazy within its own remote. The shell first loads the remote route export; that route then loads its feature chunk. The remote artifact, runtime exposed key, and compatible shared dependencies establish the integration boundary. The release pipeline still needs rollout and rollback proof.

06 · What is withComponentInputBinding()?

The exact spelling is withComponentInputBinding(). It connects matching router-state keys to inputs of the component activated by a route.

// Shell app.routes.ts loads ./Routes from mfe-orders.
// The returned ORDERS_ROUTES is mounted below path 'orders'.
// Child configuration in mfe-orders/src/app/orders.routes.ts:
{ path: ':id', loadComponent: /* load OrderDetail */ }
// The feature is enabled with provideRouter(..., withComponentInputBinding()).

// In mfe-orders/src/app/order-detail.ts
readonly id = input.required<string>();
readonly store = inject(OrdersStore);
readonly order = computed(() =>
  this.store.orders().find(o => o.id === this.id())
);
  1. The browser navigates to /orders/ORD-1048.
  2. The route matches orders/:id, producing the path parameter id = 'ORD-1048'.
  3. The router activates OrderDetail and assigns the matching id input.
  4. this.id() reads that input signal. computed derives the matching order from the domain store.
  5. The template checks loading and error first, then reads order(). Only a successful response can lead to the order or missing-resource view.

Why use it? The component declares the identifier it needs directly. It avoids manually subscribing to route parameters for this simple case. It also reacts when Angular reuses the detail component while the parameter changes.

Required is not validationinput.required<string>() declares a required input signal. It does not prove the URL contains a known order, validate user access, or fetch data. Do not read a required input in a constructor before Angular has assigned it. Our computed is evaluated when consumed after input binding.

Which router values can bind?

Matching query parameters, path/matrix parameters, static route data, and resolver data can supply inputs. If the same key occurs in multiple sources, resolver data has the highest precedence; static data outranks parameters, and path/matrix parameters outrank query parameters. For this example, ?id=OTHER does not override the path's :id.

Missing matching router data sets an input to undefined. Type annotations are not runtime data validation. For optional inputs, design defaults or transforms deliberately. Binding to arbitrary nested child components is not automatic; this feature targets routed components.

Official component input binding reference. This lesson uses the no-argument form present in our Angular 21 application; newer documentation may show additional options.

When would I use ActivatedRoute instead?

When you need route-tree relationships, navigation metadata, or explicit observable composition beyond a few component inputs. Input binding is a convenience for declaring data dependencies, not a requirement for every routed component.

13 · Debug like a principal engineer

Blank page: where should I look first?

Inspect the browser console and Network panel. Did the document load? Did the entry JavaScript load? Did bootstrap reject? Does the root selector match the HTML element? Separate server delivery, application startup, and routed component errors.

The shell is visible, but the page is missing.

Check the current URL, route matching, RouterOutlet import, and lazy chunk response. An import failure differs from a successfully loaded component with an empty view. The shell catches exposed-route loading failures with RemoteUnavailable. Later nested chunk failures or arbitrary component exceptions are outside that fallback's scope.

The order ID is undefined or the input reports it was read too early.

Check that withComponentInputBinding is enabled, the route uses :id, the input is named id, and the component is activated by the router. Do not eagerly read the required input before Angular assigns it. Confirm static/resolver data is not overriding the key.

Changing stock appears to disappear.

Inventory state now belongs to root-provided InventoryStore and survives navigation. If it disappears on refresh, that is expected: browser memory resets. Unexpected resets during navigation suggest an additional provider instance or an explicit reset command. Inspect the injection scope before adding persistence.

A status changed but the UI did not update.

Check whether the command returned a new signal value or mutated an existing object in place. Inspect the signal dependency read by the template and whether filtering legitimately hides the updated order.

The remote deployment cannot be found.

Inspect federation.manifest.json, the remote origin's remoteEntry.json response, the ./Routes exposure, MIME/CORS headers, and shared version compatibility. Start the missing remote, then reload; Angular caches loaded route configurations, including our fallback.

14 · Teach it back

Answer aloud before opening each explanation. Explaining cause and effect is more useful than memorizing API names.

1. Where does PulseOps start?

The CLI builds from mfe-shell/src/main.ts, then the browser executes the generated entry bundle. That code initializes federation, then imports bootstrap.ts to call bootstrapApplication with App and router providers. Angular mounts App on app-root and activates the URL's route in RouterOutlet.

2. Which application is the remote today?

Both mfe-orders and mfe-inventory are remotes. Each generates remoteEntry.json and exposes ./Routes. The shell loads their route arrays through loadRemoteModule at runtime.

3. What if I remove withComponentInputBinding?

The router still navigates, but it no longer populates OrderDetail.id through that feature. Our component depends on the required input, so reading it without another assignment can fail. We would need to provide the input another way, such as reading ActivatedRoute explicitly.

4. Why use computed instead of manually updating a counter?

Processing count is derived from orders. A computed tracks that dependency and avoids a second mutable value that can become inconsistent with the collection.

5. Does input.required guarantee a valid order?

No. It declares an input requirement. A URL identifier still needs validation and lookup, and the server must enforce authorization. The detail page handles an unknown identifier with a missing-order view.

6. Does loadComponent mean microfrontend?

No. It controls when a component is loaded. Our remotes have standalone builds and runtime loading, while loadComponent handles feature loading inside each remote. Release compatibility and rollout/rollback remain operational responsibilities.

7. What is the first thing you would improve?

Milestone 02 completes the asynchronous adapter and inventory store. Next introduce a lightweight backend with server validation and a real transport adapter. Federation is now implemented; next add production release compatibility checks and rollout/rollback evidence.

16 · Milestone 02: an asynchronous API boundary

The orders page no longer starts with fixtures already inside the store. It requests data through a replaceable adapter, allowing the UI to experience real asynchronous states before we introduce a network server.

Page constructor → store.ensureLoaded()
  → store.load() → status = loading, previous rows cleared
  → request Subject → switchMap
  → ORDERS_API token → FixtureOrdersApi.list(scenario)
  → wait 700 ms → rows / [] / error
  → store state signal → template chooses the correct view

Why an interface AND an injection token?

// mfe-orders/src/app/orders-api.ts — shortened
export interface OrdersApi {
  list(scenario: DemoScenario): Observable<Order[]>;
}
export const ORDERS_API = new InjectionToken<OrdersApi>('OrdersApi', {
  providedIn: 'root',
  factory: () => inject(FixtureOrdersApi)
});

// OrdersStore
private readonly api = inject(ORDERS_API);

An interface checks the TypeScript contract but disappears in JavaScript. The token is a real runtime identity Angular can resolve. The default factory supplies our fixture adapter; a test can provide a controlled fake, and a future implementation can provide a transport adapter. Production interfaces should keep demo scenario choices out of actual backend business contracts.

Why these RxJS operators?

// mfe-orders/src/app/orders-store.ts — request orchestration
this.requests.pipe(
  switchMap(scenario => defer(() => this.api.list(scenario)).pipe(
    map(orders => ({ status: 'success', orders, error: null })),
    catchError(() => of({ status: 'error', orders: [], error: '...' }))
  )),
  takeUntilDestroyed()
).subscribe(state => { /* publish state and event message */ });
  • Subject: explicit load commands enter the pipeline.
  • switchMap: a newer read unsubscribes the previous request. A late response cannot overwrite newer state. This cancels fixture timers; it does not undo committed server writes.
  • defer: calls the adapter when subscribed and lets the pipeline catch synchronous adapter exceptions too.
  • map: converts returned orders into a success state, including an empty array.
  • catchError inside switchMap: converts one failure into error state while preserving the outer stream for the next command.
  • takeUntilDestroyed: unsubscribes when the store's owning injector is destroyed. Since this store is root-provided, a route change does not destroy it.
A state machine, not several unrelated booleansOne state object holds status, orders, and error. This avoids ambiguous combinations such as loading and failed simultaneously. An empty array is a successful response; a filtered list with no matches is a separate presentation state.

ensureLoaded() loads only from idle. Returning to the page preserves loaded data, an empty response, or an error until the user explicitly reloads. The detail page calls it too, so a direct deep link works without visiting the list first. A detail lookup must wait for success before deciding the order is missing.

Tradeoff: starting a load clears old rows and temporarily hides metrics. This teaching app chooses an unambiguous loading view. A production refresh could preserve stale data with a visible refreshing indicator instead. Explicit reload also discards local simulated order changes.

Read orders-api.ts, order-fixtures.ts, orders-store.ts, then both page templates. Inventory now uses inventory-store.ts and stock-rules.ts; the page mostly delegates commands and displays state.

Official references: switchMap, catchError, takeUntilDestroyed.

Does the fixture adapter make an HTTP request?

No. RxJS timer produces an asynchronous response after 700 ms. There is no backend, transport authentication, or persistence yet. The adapter is a preparation boundary for those later concerns.

Why does “retry” load healthy fixtures?

The button explicitly requests the success scenario to demonstrate recovery. This is a learning control. A real production retry should repeat the actual failed operation rather than silently substitute fixture data.

Should switchMap handle every write command?

No. Unsubscribing does not guarantee the server canceled a write. Stock reservations and payments require deliberate concurrency and idempotency rules. Our latest-read-wins approach is for loading an order collection.

They enable standalone development. When the shell loads ./Routes, it does not execute the remote's main.ts or standalone wrapper. The host supplies the root frame and router configuration.

How do I build one remote?

Run npm run build:orders or npm run build:inventory. Outputs are complete static directories under dist/<project>/browser. The host manifest can point at a compatible remote artifact without embedding that source into the host.

19 · remoteEntry.json and loadRemoteModule()

Read these files in order: mfe-orders/federation.config.mjs, mfe-shell/public/federation.manifest.json, mfe-shell/src/main.ts, mfe-shell/src/bootstrap.ts, and mfe-shell/src/app/app.routes.ts.

The build emits remoteEntry.json, containing the name, shared package versions, and ./Routes mapping to a generated JavaScript file. This JSON is metadata, not the executable route code. Native Federation uses remoteEntry.json; Webpack's remoteEntry.js is a different format.

2. The shell knows the published location

{
  "mfe-orders": "http://localhost:4201/remoteEntry.json",
  "mfe-inventory": "http://localhost:4202/remoteEntry.json"
}

These are deployment URLs, not TypeScript path aliases. Deploy an environment-specific manifest alongside the shell. The host's own remoteEntry.json supplies its shared dependency requirements even though it exposes no business feature.

3. The initialized runtime loads the export

// app.routes.ts — simplified happy path
export const createRoutes = ({ loadRemoteModule }: NativeFederationResult): Routes => [
  {
    path: 'orders',
    loadChildren: () => loadRemoteModule('mfe-orders', './Routes')
      .then(m => m.ORDERS_ROUTES)
  }
];

mfe-orders matches the manifest remote name. ./Routes matches the exposure key. ORDERS_ROUTES is the exported JavaScript symbol inside that module. These three identifiers serve different purposes.

Why use the returned loader?Native Federation v4 returns loadRemoteModule from initFederation. Passing that runtime into the route factory keeps the dependency explicit. The older global loadRemoteModule export is deprecated; our code does not depend on it.

4. Failures are a product state

The real route loader catches an unavailable or invalid exposed route module and supplies a shell-owned fallback. Other domains remain navigable. Restore the remote and click Reload and retry; a full reload resets federation and Angular's cached route configuration. This handles entry/exposed-route loading errors, not every later feature exception.

Three distinct responsibilities

  • Angular compiles components, checks templates, and runs the application/router.
  • Native Federation builds remote metadata and exposed modules, prepares shared dependency resolution, and loads remote exports in the browser.
  • Nx can orchestrate project tasks, cache configured build outputs, visualize dependencies, and select affected work. Adding Nx does not replace federation or automatically create remote entries.

How Native Federation works — build time

  1. Each project supplies federation.config.mjs: a name, shared package requirements, and optional exposures.
  2. Orders exposes ./Routes from its orders.routes.ts. Inventory exposes the same key from its own route file.
  3. The federation builder wraps Angular's application builder and emits remoteEntry.json, exposed JavaScript, shared dependency bundles, and normal browser assets.
  4. The shell is built without importing order/inventory source. Its own entry describes its shared runtime requirements; it exposes no business route.

How Native Federation works — browser time

  1. The browser loads the shell document, import-map shim, and main.ts entry bundle.
  2. initFederation('federation.manifest.json', ...) reads deployment locations and metadata, then prepares compatible shared-module mappings.
  3. An import map associates bare package names such as @angular/core with generated module URLs. Our configuration uses es-module-shims in shim mode.
  4. The shell dynamically imports bootstrap.ts only after initialization, then calls bootstrapApplication with the returned runtime.
  5. Visiting /orders invokes the runtime's loadRemoteModule('mfe-orders', './Routes') and obtains ORDERS_ROUTES from the remote JavaScript module.
  6. Angular mounts those child routes, lazy-loads the requested page, and renders it inside the shell outlet. /orders/:id still binds to the detail component's input.
Build: config -> federation + Angular builders -> remoteEntry.json + JS
Browser: manifest -> metadata -> shared import map -> Angular bootstrap
         -> loadRemoteModule(remote name, exposed key)
         -> exported route array -> remote page in host outlet
Nx, if adopted: task graph -> run/cache those same build targets

Q25Why is switchMap appropriate for order reads but potentially dangerous for writes?

Writes require explicit ordering, duplicate handling, and server idempotency decisions rather than a blanket operator choice.

23 · A concrete shared service across shell and remotes

NotificationService is a small platform service in shared/notifications/index.ts, imported as @pulseops/notifications. The shell, orders, and inventory use it for UI notices while keeping their domain state separate.

1. Share the code identity and choose its lifetime

// Shared service declaration; implementation owns the signal queue.
@Injectable({ providedIn: 'root' })
export class NotificationService { /* ... */ }

// Singleton federation mapping in all three projects.
sharedMappings: mappingsFromWorkspace({
  singleton: true, strictVersion: true
}).only([
  '@pulseops/auth-contract', '@pulseops/notifications'
]).get()

The mapping makes every composed consumer import the same runtime class token. Angular's root provider then gives the shell and its remote pages one service instance in the host application. These are two distinct requirements: providedIn: 'root' alone cannot repair independently bundled class identities, and module sharing alone does not prevent a component from creating a child provider.

Provider ruleInject the shared service in the shell and remote consumers. Do not list it again in a remote component or route providers array unless a separate scoped instance is explicitly intended.

2. Use a narrow API

import { inject } from '@angular/core';
import { NotificationService } from '@pulseops/notifications';

const notifications = inject(NotificationService);
const id = notifications.notify('inventory', 'Local stock action completed.');
// Read messages() and latest() in consumers.
notifications.dismiss(id);
notifications.clear();

notify accepts a source (shell, orders, or inventory) and a message, then returns a numeric ID. messages() is a read-only signal collection ordered newest first and limited to five notices. latest() is computed from that queue. Dismiss removes one entry; clear empties it.

3. Follow the actual data flow

Shell welcome / Orders status action / Inventory reservation or reset
  → NotificationService.notify(source, message)
  → root-owned queue changes
  → shell notification center renders the notice
  → remote latest-notice readout sees the same queue

Shell dismiss(id) / clear()
  → same queue changes → all current consumers update

The shell owns notification presentation. The remote readout marked data-testid="remote-notification" makes the shared-instance behavior visible: changing the queue from the shell also changes what the remote reads. Publishing a notice does not mutate another domain's store.

4. Run the demonstration

  1. Restart all three applications after the new federation mapping: npm run start:all. Dependencies still install once at the root; no new package is required.
  2. Sign in using the existing demo account and observe the shell welcome message.
  3. Simulate an order update and find its Orders notice in the workspace notification center.
  4. Navigate to inventory and reserve a unit. The new Inventory notice and earlier Orders notice should be visible within the five-entry capacity.
  5. Dismiss the latest notification or clear the center. Observe the remote's latest-notice text change.
  6. Navigate away and back: the queue remains. Reload or sign out: it resets with the application.

5. Explain the standalone limit

Opening orders on 4201 or inventory on 4202 starts a separate Angular application. Its root wrapper shows its own latest notice from a separate root service instance. A standalone action does not send a notice to the shell tab, even though all applications import the same library. No cross-tab channel, persisted queue, or backend notification transport has been added.

Why not share OrdersStore and InventoryStore too?

Those stores own business state and invariants. Sharing a narrow UI-notification service supports a platform concern without letting one domain reach into another's implementation. Backend coordination and explicit domain contracts remain necessary for authoritative workflows.

What proves this is one instance rather than identical copies?

A notice published by either remote appears in the shell center, and clearing or dismissing it in the shell changes the remote readout. Test that behavior across route navigation and verify the shared mapping in all generated federation entries.

Does the five-message limit provide durable history?

No. It bounds the current UI queue. Reload discards it, and older notices are removed as capacity is exceeded. Audit history and reliable delivery belong in a backend design with different guarantees.

Read shared/notifications/index.ts, the three federation configs, workspace-layout.ts, and each remote page's publishing method. Use the current test and build output as evidence; this chapter does not claim pending verification has passed.

24 · Shared components, services, and state

Principal engineer explanationA shared component reuses presentation and interaction behavior. A shared service reuses an injectable capability. Shared state means consumers observe the same state owner at runtime. Microfrontend composition does not automatically make component instances, services, or business state global.

1. What is a shared component?

A shared component is a reusable UI building block with a small public API: inputs describe what it displays, and outputs report user interactions. Examples include a status badge, button, or notification card. It should avoid depending on the private implementation of orders or inventory.

Proposed example, not implemented in this repository: both domains could use the same status-badge component instead of repeating markup.

import { Component, input } from '@angular/core';

@Component({
  selector: 'ui-status-badge',
  template: '<span class="badge">{{ label() }}</span>'
})
export class StatusBadge {
  readonly label = input.required<string>();
}

// Consumer templates after importing StatusBadge:
// Orders:    <ui-status-badge label="Shipped" />
// Inventory: <ui-status-badge label="Low stock" />

Those two usages create two component instances. Reusing their class or template does not share their input values or local signals. Today PulseOps shares CSS such as .badge and .panel; it does not yet have this shared Angular badge component.

A component can be distributed through a versioned UI package or a deliberate federation exposure. Federation is not required for every reusable button or badge. Choose the delivery mechanism based on release needs and compatibility cost.

2. What is a shared service?

A service is an injectable capability such as notification delivery, session access, or an API adapter. A service may be stateless, or it may own state. Putting its source in a folder named shared does not by itself make every application use one instance.

// Implemented: shared/notifications/index.ts — selected lines.
@Injectable({ providedIn: 'root' })
export class NotificationService {
  private readonly state =
    signal<readonly WorkspaceNotification[]>(Object.freeze([]));
  readonly messages = this.state.asReadonly();
  readonly latest = computed<WorkspaceNotification | null>(
    () => this.messages()[0] ?? null
  );
  // notify(), dismiss(), and clear() own updates to this state.
}

In PulseOps, the shell and composed remotes import NotificationService from @pulseops/notifications. All three federation configurations share that module as a singleton, preserving the service class's identity. Angular then resolves it from the composed host application's root injector.

// Implemented federation policy in all three projects.
sharedMappings: mappingsFromWorkspace({
  singleton: true,
  strictVersion: true
}).only([
  '@pulseops/auth-contract',
  '@pulseops/notifications'
]).get()

// Shell or remote consumer:
readonly notifications = inject(NotificationService);

Two conditions matter: consumers must resolve the same runtime class/token, and they must use the same intended injector scope. Providing the service again on a component or route can create another instance even when federation shares the module.

4. Does a singleton work across standalone applications or browser tabs?

No automatic cross-application synchronization occurs. The composed orders and inventory pages run inside the shell's Angular application. Opening a standalone remote on its own port starts another Angular application with another root injector and memory. It can use the same service code while owning a different instance. Another browser tab is also a separate runtime.

A refresh resets the notification queue and domain fixtures. The demo session may restore from its same-tab marker, but that marker is not real backend authentication. Durable or cross-tab synchronization needs an explicit mechanism and, for authoritative business state, a backend.

5. What happens if the shared folder does not load in production?

The browser does not request the source shared/ folder. The build emits executable shared assets inside each project's browser output. Native Federation metadata and import maps tell the browser which generated module URL to load.
