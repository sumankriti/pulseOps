What the checked-in workflow actually does

.github/workflows/quality.yml is named Quality gates. It triggers on pushes, pull requests, and manual dispatch. Its checks job installs locked dependencies, runs npm run quality, builds all three applications, installs Chromium, and runs browser contract tests.

It saves coverage, browser-diagnostics, and the complete pulseops-browser-artifacts outputs. The separate sonar job needs successful checks, downloads the same run’s coverage, checks out full history, and executes npm run sonar:scan with the variables and secret above.

Existing Sonar gate behavior · explanation, not new YAML to paste 
SONAR_ENABLED absent or not true -> Sonar job skipped
Checks fail                      -> Sonar job not reached
Push / same-repository PR        -> Sonar job runs when enabled
Fork PR                          -> Sonar job skipped
Scanner or server gate fails     -> Sonar job fails
No deployment job                -> Nothing is published to AWS

Plan checkpoint: the current workflow scans all pushes and eligible same-repository PRs. Sonar Cloud Free currently limits branch analysis to main and PR analysis to PRs targeting main. A feature-branch push can therefore require a later workflow-policy change. Confirm the selected plan and intended branch policy before enabling scans; no such change is made by this HTML update.

  1. Ensure the intended quality.yml is published to the default branch through a reviewed PR.
  2. Open Actions → Quality gates → Run workflow, selecting main for the first full scan.
  3. Inspect the checks log, the Sonar job, retained coverage, browser diagnostics, and the server analysis. Verify the job ran; a skip does not establish a pass.
  4. After actual runs exist, configure a ruleset/branch protection for main and require Lint, coverage, build, and browser contracts.
  5. Require the real Sonar gate once its supported PR/branch analysis policy is in place. Establish how fork contributions are reviewed without distributing scan tokens to untrusted code.
  6. Review Dependabot PRs under the same checks. A proposed coverage/new-code policy must be configured in Sonar itself.

Success criteria: the configured checks actually run on the intended branch/PR, a bad change is blocked by the expected gate, and the successful artifact belongs to the reviewed commit. A GitHub skipped job may still report success, so merely marking an optional job required is not sufficient enforcement.

G · AWS CD plan: S3, CloudFront, and GitHub OIDC

Current state: CI exists; CD is still a plan. The current workflow saves browser artifacts and has no AWS deployment job. The source shell manifest still contains localhost URLs. The steps below explain the user changes needed before a public deployment; they do not create resources or modify this project.

1. Choose the hosting resources

Select the AWS account and S3 region, then create three globally unique bucket names and one CloudFront distribution per application. Record bucket names, distribution IDs, and HTTPS domains.

Application Complete output to publish Suggested topology
Shell dist/mfe-shell/browser/ Private S3 bucket and shell CloudFront distribution.
Orders remote dist/mfe-orders/browser/ Private S3 bucket and orders CloudFront distribution; immutable release prefixes.
Inventory remote dist/mfe-inventory/browser/ Private S3 bucket and inventory CloudFront distribution; immutable release prefixes.
  1. Keep S3 Block Public Access enabled. Use normal S3 REST origins with CloudFront Origin Access Control and bucket policies restricted to each distribution.
  2. Enable HTTPS/HTTP-to-HTTPS redirects. S3 website endpoints do not support this OAC setup.
  3. Configure CORS on remote responses for the shell origin, including JavaScript/shared chunks and metadata JSON.
  4. Configure shell SPA navigation such as /orders to serve root /index.html. Preserve missing-asset errors for .js, .json, and other resources.
  5. Cache immutable release assets long-term; revalidate mutable shell/index/manifest pointers. Retain older assets for open tabs and rollback.

2. Prepare GitHub-to-AWS authentication

Create a protected GitHub environment called production and restrict it to the deployment branch. Configure AWS IAM trust for GitHub OIDC, audience sts.amazonaws.com, and the exact subject used by this repository’s production environment. Grant the deployment role only the required S3 publication and CloudFront invalidation access.

OIDC subject checkpoint: GitHub’s current subject format may include immutable owner/repository IDs for newer or opted-in repositories. Match the actual emitted subject; do not blindly copy a generic repo:owner/repository:environment:production value. A deployment job also needs id-token: write to obtain the short-lived identity.

Proposed deployment values Purpose Status
AWS_REGION, AWS_ROLE_ARN Region and OIDC deployment role. Not consumed by the current workflow; needed by a future deployment job.
Three bucket names Where each complete app release is published. Choose/create in your account; do not assume suggested names are available.
Three distribution IDs / domains HTTPS delivery, manifest URLs, and any targeted invalidation. Record from actual CloudFront resources.

3. Promote releases in the correct order

CI + actual Sonar pass→Download checked artifact→Publish remote releases→Verify chunks→Promote shell + manifest→Smoke test

Publish the complete remote browser directories to immutable release paths first. Validate remoteEntry.json and its referenced assets. Then supply the shell’s deployment-artifact manifest with the real remote release URLs. The following shows the intended shape, not values already configured:

Proposed production federation.manifest.json · replace with actual release URLs later 
{
  "mfe-orders": "https://YOUR_ORDERS_DISTRIBUTION.cloudfront.net/releases/RELEASE_ID/remoteEntry.json",
  "mfe-inventory": "https://YOUR_INVENTORY_DISTRIBUTION.cloudfront.net/releases/RELEASE_ID/remoteEntry.json"
}

Keep the shell’s complete output at its expected root, including its own federation metadata. Uploading only a remote entry or a source shared/ directory is insufficient; the browser needs every referenced chunk. Deployment should promote the checked build, not silently rebuild application code.

4. Define deployment acceptance and rollback

Smoke-test login, orders, inventory, shared-session behavior, deep-link refresh, remote outage/retry, and logout on the actual HTTPS URLs. Record the shell/remote release set. Rollback should restore a tested shell/manifest pointer while retained remote assets remain reachable. Review existing demo authentication separately before handling real users.

Success criteria: a failed CI/Sonar gate prevents publication, the deployed manifest references only verified assets, the browser completes the required journeys, and rollback is demonstrated. Exact AWS CLI/workflow instructions come after your account region, resource names, role, and domains are known; the assistant will guide rather than apply them.

eslint.config.mjs · new Angular CLI app
import eslint from '@eslint/js';
import tseslint from 'typescript-eslint';
import angular from 'angular-eslint';
import prettier from 'eslint-config-prettier';

export default tseslint.config(
  {
    ignores: [
      '**/node_modules/**', 'dist/**', '.angular/**',
      'coverage/**', 'playwright-report/**', 'test-results/**',
      '.scannerwork/**',
    ],
  },
  {
    files: ['**/*.ts'],
    extends: [
      eslint.configs.recommended,
      ...tseslint.configs.recommendedTypeChecked,
      ...angular.configs.tsRecommended,
    ],
    languageOptions: {
      parserOptions: {
        projectService: true,
        tsconfigRootDir: import.meta.dirname,
      },
    },
    processor: angular.processInlineTemplates,
    rules: {
      '@typescript-eslint/no-explicit-any': 'error',
      '@typescript-eslint/no-floating-promises': 'error',
      '@typescript-eslint/no-misused-promises': 'error',
      '@typescript-eslint/consistent-type-imports': 'error',
      eqeqeq: ['error', 'always'],
    },
  },
  {
    files: ['**/*.html'],
    extends: [
      ...angular.configs.templateRecommended,
      ...angular.configs.templateAccessibility,
    ],
    rules: { '@angular-eslint/template/no-any': 'error' },
  },
  prettier,
);

projectService reads TypeScript project information. Keep application and test files included in their generated tsconfigs. If ESLint reports that a file is outside the project, correct the tsconfig or scope the rule block to actual application files. Add a separate Node/JavaScript ruleset if you introduce tooling scripts.

Verify the policy · terminal

# Review changes after using automatic fixes:
npx eslint "src/**/*.{ts,html}" --fix

Expected result: exit code 0 with no warnings. An intentional any or an unhandled promise should make lint fail. Use --fix locally; CI should report failures without rewriting the checked-out source.

scripts/sonar-scan.mjs
import { readFile } from 'node:fs/promises';
import { scan } from '@sonar/scan';

try {
  const required = ['SONAR_HOST_URL', 'SONAR_PROJECT_KEY', 'SONAR_TOKEN'];
  const missing = required.filter((name) => !process.env[name]?.trim());
  if (missing.length) throw new Error(`Missing settings: ${missing.join(', ')}`);

  const lcov = await readFile('coverage/quality-lab/lcov.info', 'utf8');
  if (!lcov.includes('SF:')) throw new Error('Generate valid LCOV coverage first.');

  await scan({
    serverUrl: process.env.SONAR_HOST_URL,
    token: process.env.SONAR_TOKEN,
    options: {
      'sonar.projectKey': process.env.SONAR_PROJECT_KEY,
      ...(process.env.SONAR_ORGANIZATION
        ? { 'sonar.organization': process.env.SONAR_ORGANIZATION }
        : {}),
    },
  });
} catch {
  console.error('Sonar scan failed. Check settings, coverage, scanner output, and quality gate.');
  process.exitCode = 1;
}

The catch message deliberately avoids printing settings or tokens. Run the scanner from the workspace root. The provider reads sonar-project.properties there.

Local scan · replace non-secret values
export SONAR_HOST_URL='https://YOUR-SONAR-HOST'
export SONAR_PROJECT_KEY='YOUR_PROJECT_KEY'
# Cloud only; omit for Server unless its setup requires it:
export SONAR_ORGANIZATION='YOUR_ORGANIZATION_KEY'

# Enter the token privately; bash and zsh support this prompt:
printf 'Sonar analysis token: '
read -r -s SONAR_TOKEN
printf '\n'
export SONAR_TOKEN

npm run test:coverage
npm run sonar:scan
unset SONAR_TOKEN

Expected result: the server shows this commit’s analysis and imported coverage, and the command waits for the quality gate. Define the new-code period, quality profile, and gate in Sonar. A proposed policy is no new reliability/security issues, reviewed new hotspots, at least 80% new-code coverage, and at most 3% new-code duplication. Installing the scanner does not create these policies.

10 · Add the GitHub Actions CI workflow

Create .github/workflows/ci.yml. This complete starter runs local quality checks and a production build on PRs and main. On main, a second job imports the same run’s coverage and requires a real Sonar gate result. No Sonar token is passed to PR code.

.github/workflows/ci.yml · single-app starter 
name: Angular product pipeline

on:
  pull_request:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  checks:
    name: Quality checks
    runs-on: ubuntu-latest
    timeout-minutes: 20
    env:
      CI: true
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
        with:
          persist-credentials: false
      - uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          node-version-file: .nvmrc
          cache: npm
      - run: npm ci
      - run: npm run quality
      - run: npm run build
      - name: Save coverage for analysis
        uses: actions/upload-artifact@b7c566a772e6b6bfb58ed0dc250532a479d7789f # v6
        with:
          name: unit-coverage
          path: coverage/
          if-no-files-found: error
          retention-days: 7
      - name: Save the exact browser build
        uses: actions/upload-artifact@b7c566a772e6b6bfb58ed0dc250532a479d7789f # v6
        with:
          name: quality-lab-browser
          path: dist/quality-lab/browser/
          if-no-files-found: error
          retention-days: 7

  sonar:
    name: Main Sonar gate
    needs: checks
    if: github.event_name != 'pull_request' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
        with:
          fetch-depth: 0
          persist-credentials: false
      - uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          node-version-file: .nvmrc
          cache: npm
      - run: npm ci
      - uses: actions/download-artifact@37930b1c2abaa49bbe596cd826c3c89aef350131 # v7
        with:
          name: unit-coverage
          path: coverage
      - name: Analyze and wait for the quality gate
        run: npm run sonar:scan
        env:
          SONAR_HOST_URL: ${{ vars.SONAR_HOST_URL }}
          SONAR_PROJECT_KEY: ${{ vars.SONAR_PROJECT_KEY }}
          SONAR_ORGANIZATION: ${{ vars.SONAR_ORGANIZATION }}
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}

Why these choices: npm ci uses the lockfile; the build and coverage artifacts belong to this run; full history helps Sonar’s new-code analysis; pinned action commits reduce unexpected changes; jobs have timeouts and minimal permissions. Use Dependabot to review updates to those pins.

Scope of enforcement: the starter gates PR merges with Quality checks and gates deployment with the successful Main Sonar gate. It does not claim to run Sonar PR analysis. Add that later if your Sonar product/plan supports it and your organization has a trusted PR-scanning policy. A skipped Sonar job is not evidence that a quality gate passed.

For integration journeys, add Playwright after configuring a test server and writing meaningful tests. Then put npx playwright install --with-deps chromium and npm run test:e2e before uploading the deployable artifact. PulseOps already has this browser contract layer.

14 · Extend the pipeline for production microfrontends

Federation changes what must be released together. The shell, each remote, shared packages, runtime manifest, and complete federation output all need explicit ownership and compatibility checks.

Decision Production approach Evidence to collect
Build and package Create an immutable release directory per shell/remote and commit SHA. Upload the complete browser output, including federation metadata and shared chunks. Artifact inventory, hashes, and release identity
Deploy order Publish and verify remote assets first. Promote a manifest referencing those releases only after they are reachable and compatible. Remote entry/chunk fetches and composed browser smoke tests
Shared dependencies Agree Angular/RxJS/shared-contract singleton versions. Test allowed host/remote combinations before promotion. Version compatibility matrix and shared-session tests
Runtime URLs Use environment-specific HTTPS manifest URLs. Configure remote asset CORS, MIME types, CSP, and SPA fallback on the chosen CDN. Cross-origin loading and deep-link refresh tests
Caching Cache immutable hashed assets for a long period. Revalidate the mutable manifest/entry according to the release strategy. Observed response headers and cold-load network tests
Rollback Retain older referenced assets. Roll the manifest/shell pointer back to a tested compatible release set. Rollback rehearsal and recovery-time evidence
Access and promotion Use protected environments and short-lived platform identity, such as OIDC, where supported. Least-privilege deployment role and auditable approval
Operations Attach host/remote release IDs to telemetry. Exercise remote outage and recovery, login expiry, and navigation after logout. Alerts, ownership, runbook, and browser journey results

Why a shared folder is not a deployment unit: source code is bundled or federated into browser artifacts. Deploying a source folder does not deliver a shared service to the browser. Inspect the generated federation metadata/chunks and deploy every referenced asset.

A common CI entry point for a workspace is npm run quality && npm run build && npm run test:e2e, with those scripts orchestrating the shell, all remotes, and shared contracts. Each independently deployed remote must also prove compatibility with the supported shell versions.

Before a real product launch, complete backend authorization, secure session handling, tenant boundaries, monitoring, and incident recovery. Static analysis and pipeline gates provide evidence about code quality; the architecture still needs those operating capabilities.
